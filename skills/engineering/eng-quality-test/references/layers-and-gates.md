# 分层、责任与证据门禁

## 选择层级而非堆叠层级

| 层级 | 要证明什么 / 最小证据 | 增量触发 | 不足以证明什么 |
| --- | --- | --- | --- |
| unit | 受影响函数/组件的不变量、边界和错误分支；具名断言 | 行为逻辑变化，例如数量上限、幂等键计算 | 系统可启动、完整用户 AC、跨服务兼容 |
| smoke | 当前产物可加载/启动并走一条最短关键路径；实际退出码和观测 | 交接新构建/配置/候选时；纯文档可用结构检查 | 业务边界正确、所有测试通过 |
| feature | 单 feature 的 AC 成功/拒绝/状态变化；按范围选择本地/隔离环境 | 用户行为或单功能流程变化 | 多候选组合与外部契约兼容 |
| integration | 真实受影响边界的请求/响应、数据与失败恢复；消费者证据 | 接口、共享 schema、跨模块调用、公共基础依赖或多候选相互作用改变 | 完整发布质量、所有无关模块正确 |
| release regression | 发布流程定义的版本级回归集合与环境检查 | 明确发版/全回归授权或仓库正式发布门禁 | 自动允许部署/生产写入 |

smoke 是可运行前提，不用它替代受影响 unit/feature；integration 不等于全仓测试。测试层级取决于验证对象，不只看目录名称。mock contract 只能证明模拟契约；没有真实边界证据时不能改名成 integration pass。

局部例子：`MAX_QTY 5→9` 且调用/错误码不变，选择边界 unit、加载 smoke、提交/拒绝 feature；若库存消费者仍假定 5，则追加其确切契约验证并记录跨边界触发原因。不要因为“购物车很重要”直接要求 release regression。

## 开发 / 单流水 / 多流水责任矩阵

“负责”包括提供或委派明确的执行者，不代表所有角色都重跑。`eng-quality-test` 负责计划、证据分类和报告，不取得候选合并/发布权。

| 事项 | 开发者 / 工作分支 | 单流水负责人 | 多流水 / 唯一集成人 |
| --- | --- | --- | --- |
| unit | 写或补受影响断言，运行有界选择器，修复失败 | 检查 AC/风险映射与当前证据 | 只重跑组合改变的不变量；其余按证据复用规则处理 |
| smoke | 当前变更可加载/运行 | 针对最终 candidate 核对版本及关键路径 | 冻结最终集成 head 后最短组合 smoke |
| feature | 在隔离环境证明当前 feature AC | 对必需 AC 闭环负责；缺关键结果不出就绪候选 | 复用未受影响 AC；组合影响部分重验 |
| integration | 标出边界/消费者，准备契约及隔离数据 | 有跨边界触发时安排有界验证，不能漏给多流水 | 按冻结候选集负责实际交互验证，不逐候选全回归 |
| release regression | 不默认执行 | 不因 feature 交接自动启动 | 只有明确 release 门禁的责任人安排；先核预算和权限 |
| 计划评审 / 失败处理 | 作者自查，失败归因并最小修复 | 指定独立评审者；决定候选是否满足阶段门禁 | 处理组合冲突，冻结新 head；超预算关本轮或退回责任人 |

仓库 AGENTS 已覆盖旧“工作分支只 smoke、集成必全回归”默认。计划必须写明当前阶段负责人、执行者、独立评审者、下一责任人；缺人员时可先草拟，不假装完成审批。

## 测试方案的可操作阻断点

| 证据检查 | 何时 revise / blocked | 最小解除条件 |
| --- | --- | --- |
| AC→case→断言 | 已知 AC 没有判定断言为 revise；AC 未提供为 blocked | 对应 AC 有步骤、期望状态/输出、错误边界 |
| 选择器 / 层级 | 命令包含全仓或测试零发现但宣称覆盖为 revise | 从真实测试配置确认有界选择器、预期测试数/识别方式 |
| 环境 / 数据 | 必需 sandbox 不可用、只能用生产或权限不足为 blocked | 获得本地/隔离替代环境与许可，不需要把凭据写进计划 |
| revision / 复用 | 对象不明为 blocked；把已知 stale pass 当当前结果为 revise | 明确 commit 或 dirty 内容摘要与文件摘要，完成影响分析 |
| 预算 / 责任 | 必需集合超预算或无人执行/评审为 blocked | 获批小幅预算/责任人或有理由缩小交付目标，不能偷偷丢 AC |

所有发现沿用 [公共 review envelope](../../../../docs/contracts.md)，不能只写“覆盖不够”“测试需加强”。例如：`REV-001 major evidence=test-plan#AC-003 impact=拒绝后仍可能写入 minimal_fix=加无状态变化断言 owner=cart-dev acceptance=10 被拒绝且持久层写次数为 0`。

## 证据与状态

每个结果至少记录：`case_id`、AC/风险、层级、是否本阶段必需、`status`、`execution_origin`、对象 revision/摘要、执行者、命令与 cwd/人工步骤、开始/结束时间、退出码（不能适用时 null）、实际断言、证据路径、未完成原因。未知值写 null 加原因，不补造命令、时间或日志。

| case status | 成立条件 | 常见误记 |
| --- | --- | --- |
| pass | 真正执行且预定断言通过，有可核验证据；复用仅按下述规则 | 退出码 0 但零测试、只生成计划、只阅读代码均不能算 |
| fail | 已执行，观察到断言失败/被测产物错误，能定位证据 | 缺工具/环境不是产品断言失败 |
| blocked | 因具体依赖、权限、工具/环境问题无法开始或完成判定 | 将已确定失败改为环境阻断隐藏错误 |
| not_run | 尚未开始，如仅规划、未选入本轮、预算不足；写原因 | 已中断/超时的运行应为 blocked，而不是假装没运行 |

`execution_origin` 区分 `executed/reused/fixture/planned`；`freshness` 区分 `current/stale`，它们不是新 status。fixture 可有模拟 pass/fail，但永不能满足真实门禁。dry-run 只证明计划/命令组装；未实际覆盖的 case=not_run。手工执行也要步骤和实际观测，无退出码不妨碍有证据的手工 pass。

单命令执行多个 case 时保留每个 case 的实际结果。退出码非零不能自动把所有子用例记 fail；无子用例证据则 blocked。退出码 0 且零测试发现时记 not_run 并阻断必需覆盖。失败后通过保留全部 attempts；flaky 未定位时标明风险，由门禁负责人按 AC 判断，不删第一次失败。

## 绑定与复用

1. 有提交时实际读取 `git rev-parse HEAD` 和 dirty paths；代码、测试、锁文件/配置及相关数据进入受测文件清单。未提交的 commit 字段写 `uncommitted`，artifact_revision 仍是从 1 开始的正整数，另记内容摘要及实际 SHA-256；删除文件记 tombstone，新文件必须纳入。基线必须来自实际 repo，不从示例复制 hash。
2. 环境另记运行时/依赖版本、配置摘要、数据 fixture 版本、服务版本，排除秘密。运行前后比较内容摘要与环境；发生变化则记录漂移、标 stale，不能把日志改绑新版本。
3. 同一提交也可能因环境/数据变更而失效。跨 revision 复用须逐 case 列“不受影响”的路径/依赖/环境依据、原始日志、来源 revision、责任人；不能仅凭测试文件没改就复用。
4. 冻结集成 head 与候选各自 commit 不同；候选结果不是集成结果。先分析组合影响，针对最终 head 运行批准的集成集合。最终提升对象变了就重新评估，不冒用旧结论。

## 报告门禁与停止

报告分别统计必需和非必需的 pass/fail/blocked/not_run，另列 stale/fixture 数量（与状态统计可交叉，不混为总和）。未触发的 integration/release 可以放 `not_selected` 附理由，不伪造用例凑通过数。

- 有当前必需的确定 fail：结论 `revise`，同时保留其他 blocked/not_run；把最小修复交开发者。
- 无确定 fail，但任一必需 blocked/not_run/stale、无法核验版本、缺独立计划评审或证据只有 fixture：真实交接 `blocked`。
- 全部本阶段必需 case 有当前、真实或合规复用的 pass，计划门禁已过且无未解决重要风险：可给该**阶段测试结论** `pass`，列范围和排除项。
- 非必需项出现安全/数据/AC 相关失败必须重新评估风险，不能以“optional”跳过；缩范围需要责任人确认，保留原失败。

只交付计划时可以给“计划交付完成”，但不能生成测试通过结论。计划、用例或一次 smoke 都不等于研发、集成、部署已成功。预算不足、无权限、重复失败或达到验收后即停；新增范围交责任人决策，不递归调用其他 skill。
